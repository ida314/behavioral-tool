# Decisions

Choices the spec left open, resolved so implementation is not blocked. Each entry says
what was decided, why, and what would make us revisit it.

If you disagree with one of these, change it deliberately and update this file — do not
quietly diverge. Where a decision deviates from [SPEC.md](./SPEC.md), it says so.

---

## ADR-001 — Next.js 16 (App Router), TypeScript, Tailwind v4

**Decided.** Matches the reference stack in SPEC §13. Scaffolded with `create-next-app`
using `src/`, the App Router, and the `@/*` import alias.

**Notes for anyone writing code here:**

- Next 16 is **not** the Next.js in your training data. `params` and `searchParams` are
  Promises — `const { questionId } = await props.params`. Same for `cookies()`,
  `headers()`, `draftMode()`. Synchronous access was removed in 16.
- Route prop types are **globally generated**: `PageProps<"/attempts/[attemptId]">`,
  `LayoutProps<"/">`. Do not hand-write prop interfaces for pages; run
  `npx next typegen` if the types look stale.
- Turbopack is the default bundler in 16.
- Authoritative docs ship in the repo at `node_modules/next/dist/docs/`. Read those
  rather than recalling API shapes.

## ADR-002 — Prisma 7 + PostgreSQL in Docker

**Decided.** Prisma over Drizzle (SPEC §13 allows either) because SPEC §28 already
specifies a Prisma schema, so it is the lower-friction path. Local Postgres runs from
`docker-compose.yml` on **host port 5433** to avoid colliding with any other local
Postgres.

**Prisma 7 differs sharply from Prisma 5/6 — this trips people up:**

| Thing | Prisma 7 reality |
| --- | --- |
| Generator | `prisma-client` (not `prisma-client-js`) |
| Client location | `src/generated/prisma/` — gitignored, regenerated by `postinstall` |
| Import path | `@/generated/prisma/client`, **not** `@prisma/client` |
| Datasource URL | lives in `prisma.config.ts`, not in `schema.prisma` |
| Engine | none — a **driver adapter is required**: `new PrismaClient({ adapter: new PrismaPg({ connectionString }) })` |

All of that is already wired up in `src/lib/db.ts`. Import `db` from there; never
construct a `PrismaClient` anywhere else.

**Revisit if:** we move to a serverless Postgres that wants a different adapter
(e.g. Neon's), which is a change to `src/lib/db.ts` alone.

## ADR-003 — Dev-stub authentication now, managed provider in Phase 5

**Decided.** SPEC §13 calls for a managed auth provider and SPEC §20 demands strict
per-user scoping. Those are two separate requirements, and only the second one affects
how feature code is written.

So: **all identity flows through `requireUser()` in `src/lib/auth.ts`**, which currently
returns one seeded local user. Every query is written user-scoped from day one. Wiring a
real provider later is a change to that single file — no feature code moves.

**Why not Clerk/Auth.js immediately:** it would gate Phases 1–4 behind provider
credentials and a signup flow, for zero learning about the product loop. The MVP question
(SPEC §34) is whether practice history is useful, not whether login works.

**This is a deviation from SPEC §29 step 1 ("Create account").** Real auth is required
before the MVP is shippable to anyone but the developer, and it is scheduled in
Phase 5 of [IMPLEMENTATION_PLAN.md](./IMPLEMENTATION_PLAN.md). Do not ship publicly
without it.

**The rule that must not be broken meanwhile:** never accept a user id from a request
body, query string, form field, or component prop. Always
`const user = await requireUser()` and scope on `user.id`.

**`requireUser()` calls `connection()` first**, which opts every caller out of static
prerendering. Without it, Next prerenders pages that read only user-owned data (`/`,
`/progress`, `/stories`) at build time and serves one user's data as static HTML — a
bug the single-user dev stub hides completely. A real auth provider reads the request
and forces this anyway, so it is true from the start. Check it with `npm run build`:
every route should print `ƒ (Dynamic)`.

## ADR-004 — Deterministic question IDs instead of `cuid()`

**Decided.** `Question.id` is an explicit string like `q_conflict_01`, assigned in
`src/data/questions.ts`, rather than a generated cuid.

**Why:** the seed must be re-runnable. With stable ids, `npm run db:seed` upserts and
existing `PracticeAttempt.questionId` references survive. With cuids, re-seeding would
either duplicate the bank or orphan every historical attempt — which would destroy the
one thing this product exists to accumulate.

**Rules:** never renumber an id, never reuse a retired one. To retire a question, delete
its entry from `questions.ts` and leave the id burned. (Deleting the row from the DB
would break attempts that reference it; prefer leaving the row in place.)

This is a small deviation from SPEC §28, which had `@default(cuid())` on `Question.id`.
`Story` and `PracticeAttempt` keep `cuid()` as specified.

## ADR-005 — Server Components + Server Actions; no REST layer in the MVP

**Decided.** Reads happen in Server Components calling query functions directly; writes
happen through Server Actions. We are **not** building the `/api/*` route handlers in
SPEC §14–§17 for the MVP.

**Why this is in-spec:** SPEC §14 opens with _"If using REST-style routes"_ — the HTTP
API is conditional, and SPEC §13 explicitly permits server actions. No acceptance
criterion in SPEC §29 requires an HTTP endpoint. Building both a REST layer and the
server-rendered UI would roughly double the surface area for no MVP value.

**The constraint that keeps this reversible:** all data access lives in
`src/lib/queries/` (reads) and `src/lib/actions/` (writes) — never inline in a component.
Adding `/api/*` later becomes thin handlers over the same functions, and the request and
response shapes in SPEC §14–§17 remain the contract to implement when that day comes.

**Revisit if:** a mobile client, a public API, or client-side fetching becomes a
requirement.

## ADR-006 — Practice session gets its own route

**Decided.** `/practice/[questionId]` (SPEC §8.3 permits either this or local state).

**Why:** attempt detail needs a "Practice this question again" link, which needs a URL.
It also survives a refresh mid-answer.

The **Save Attempt** step (SPEC §8.4) is a second stage *within* that same page — a
client component that swaps from editor to save panel while holding the response in
state. One server action fires at the end. This directly serves SPEC §24: the response
must never be lost, so it stays in client state until the save succeeds.

## ADR-007 — Delete behavior

**Decided.**

- `PracticeAttempt.story` → `onDelete: SetNull`. Deleting a story must never delete
  practice history (SPEC §16).
- `Story.user` and `PracticeAttempt.user` → `onDelete: Cascade`. Deleting a user removes
  their own data; there is no reason to retain orphans.
- `PracticeAttempt.question` → **restrict** (Prisma's default). Questions are
  system-owned and must not disappear from under an attempt (see ADR-004).

## ADR-008 — Analytics is a no-op shim for now

**Decided.** SPEC §25 names six events. Implement `track(event, props)` in
`src/lib/analytics.ts` as a typed function that logs in dev and does nothing in
production, and **call it at the right places from the start**.

**Why:** the call sites are the expensive part and they are easy to place correctly while
building each flow, impossible to retrofit accurately later. Choosing a vendor is a
one-file change once there are users to measure.

## ADR-009 — Validation with Zod at the action boundary

**Decided.** Every server action parses its input with a Zod schema from
`src/lib/validation.ts` before touching the database, implementing SPEC §19.

`response` is capped at 20,000 characters — comfortably above any real interview answer,
below anything that would be abusive. SPEC §19 says only "reasonable database limit".
